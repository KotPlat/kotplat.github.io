KotPlat / roomQL

roomQL

Kotlin · Apache-2.0 · v2.0.0

A type-safe Kotlin DSL for building dynamic Android Room queries at runtime — no raw SQL strings, no reflection, no 2n DAO methods.

Install Quick start API overview FAQ Full usage guide ↗ Full API reference ↗

A query whose filter values vary at runtime already has a static answer in Room: WHERE (:minAge IS NULL OR age >= :minAge), checked at compile time. A query whose structure varies — which column to sort or group by, whether a join is present, which columns to project — is harder: SQL can bind a value as a parameter, never an identifier, so a static @Query reaches it only through a CASE ladder, or not at all for a dynamic SELECT list. roomQL covers both with one typed DSL: a KSP processor generates a Column<T> for every column in your @Entity classes, so orderBy, groupBy, join, and select take real, rename-safe Kotlin symbols, and a null filter drops out of the generated SQL. You keep Room’s @RawQuery.

Installation

roomQL is published on Maven Central under io.github.kotplat.roomql. Declare the version catalog entries (gradle/libs.versions.toml):

[versions]
roomql = "2.0.0"

[libraries]
roomql-runtime-android = { module = "io.github.kotplat.roomql:runtime-android", version.ref = "roomql" }
roomql-ksp-processor   = { module = "io.github.kotplat.roomql:ksp-processor",   version.ref = "roomql" }
plugins {
    id("com.google.devtools.ksp")
}

dependencies {
    implementation(libs.roomql.runtime.android)   // .toQuery() bridge; pulls in :runtime
    ksp(libs.roomql.ksp.processor)                // generates the *Table objects
}

That is the whole dependency block for Android. runtime-android already depends on runtime (the query { } DSL), so it comes along automatically. The ksp(...) line stays separate because Gradle cannot pull a symbol processor in transitively. Add io.github.kotplat.roomql:runtime directly only if you want the DSL without the Room bridge, for example to unit-test generated SQL on the plain JVM.

Minimal working example

import androidx.room.Dao
import androidx.room.Entity
import androidx.room.PrimaryKey
import androidx.room.RawQuery
import androidx.sqlite.db.SupportSQLiteQuery
import com.roomql.android.toQuery
import com.roomql.runtime.SortDirection
import com.roomql.runtime.query

@Entity(tableName = "users")
data class UserEntity(
    @PrimaryKey val id: Int,
    val name: String,
    val age: Int,
    val status: String,
)
// KSP generates UserEntityTable in the same package.

@Dao
interface UserDao {
    @RawQuery
    fun search(q: SupportSQLiteQuery): List<UserEntity>
}

fun searchUsers(dao: UserDao, minAge: Int?, status: String?): List<UserEntity> {
    val q = query {
        from(UserEntityTable)
        where {
            UserEntityTable.age gteIfNotNull minAge      // dropped from the SQL when minAge is null
            UserEntityTable.status eqIfNotNull status    // dropped from the SQL when status is null
        }
        orderBy(UserEntityTable.age, SortDirection.DESC)
        limit(20)
    }
    return dao.search(q.toQuery())
}

searchUsers(dao, 18, "active") runs SELECT * FROM users WHERE age >= ? AND status = ? ORDER BY age DESC LIMIT 20. searchUsers(dao, 18, null) drops the status filter. searchUsers(dao, null, null) drops both — no if ladders, no IS NULL OR trick.

Dynamic structure: a runtime sort column

A runtime-chosen sort column has a static workaround — ORDER BY CASE WHEN :sortBy = 'age' THEN age WHEN :sortBy = 'name' THEN name END, bound to a string — but it becomes hard to maintain once a second axis, such as an optional join or filter, needs to vary with it. roomQL takes a typed column instead:

fun sortedUsers(dao: UserDao, sortColumn: Column<*>, direction: SortDirection): List<UserEntity> {
    val q = query {
        from(UserEntityTable)
        orderBy(sortColumn, direction)
    }
    return dao.search(q.toQuery())
}

sortedUsers(dao, UserEntityTable.age, SortDirection.DESC)
sortedUsers(dao, UserEntityTable.name, SortDirection.ASC)

For a single, fixed set of sort columns, a when dispatch is a good zero-dependency alternative. roomQL pays off when sorting has to compose with an optional join, a runtime groupBy, or a chosen select(...) projection.

What you get

  • Dynamic query structure, typed. orderBy, groupBy, join, and select take a real Column<T>/Expression<T> instead of a CASE ladder or a bare string.
  • Compile-time safety on column references. Renames and typos fail the build instead of the query.
  • Optional filters that disappear, and say so. IfNotNull operators skip the condition when a value is null; the plain operators are required and won’t compile against a nullable value.
  • A real DSL, not string concatenation. where, or { }, orderBy, limit/offset, groupBy/having, select, join. Values bind as positional ? parameters.
  • Aggregates and explicit projections. count, countAll, sum, avg, min, max work in having { } and orderBy; select(...) projects them or specific columns. @Projection generates a typed factory for a multi-column result class, so a missing field is a compile error.
  • Automatic JOIN column aliasing. Colliding column names across joined tables are aliased (users.id AS users__id) so a cursor never silently overwrites a column.
  • Works with Room’s own @RawQuery. Blocking, suspend, and Flow return types all work.

Use roomQL when more than one axis of a query — sort, grouping, join, projection, filters — needs to vary together, or when you want one typed vocabulary instead of a CASE ladder for structure and an IS NULL OR ladder for values. Skip it for fully static queries (a plain @Query gives full compile-time SQL verification), for a single small axis a when dispatch already covers, or for shapes it doesn’t build: DISTINCT, subqueries, or UNION.

FAQ

Does roomQL replace Room?

No. roomQL sits on top of Room and produces the SupportSQLiteQuery that Room’s own @RawQuery methods take. You keep your entities, database, DAOs, and migrations exactly as they are.

Is roomQL safe from SQL injection?

Values are always bound as positional ? parameters, never interpolated into the SQL text. The one exception is the raw-string from("table_name") overload — never pass an untrusted string to it.

Does roomQL use reflection or runtime code generation?

No. The KSP processor generates typed column references at build time; the runtime is a plain string builder over those references, so R8/ProGuard needs no extra keep rules.

Why three modules instead of one?

runtime is pure JVM so generated SQL is unit-testable with no emulator. runtime-android is the thin Android bridge, and ksp-processor runs at build time only. In practice you declare two dependencies, not three: runtime-android pulls in runtime transitively.

Does roomQL work with Kotlin Multiplatform?

Not yet. runtime is a plain JVM module, not a KMP source set, and runtime-android depends on androidx.sqlite. roomQL targets Android and JVM projects that use Room.

Does roomQL support KAPT?

No — roomQL ships a KSP processor only. Room itself can still run on KAPT in the same module if you haven’t migrated it yet.

Does roomQL validate my SQL at compile time?

Only the column references. A renamed or deleted column is a compile error, but Room’s @RawQuery skips Room’s static SQL verification, so a logically wrong query (a bad join predicate, a groupBy that doesn’t match the projection) surfaces at runtime. For static queries, a plain @Query remains the safer choice.

Why doesn’t my Flow re-emit when the table changes?

Room cannot infer which tables a raw query touches, so a Flow-returning @RawQuery must list them: @RawQuery(observedEntities = [UserEntity::class]). This is a Room requirement, not a roomQL one.
